Nearest-neighbor search: from brute force to HNSW

Search engines, recommenders and Retrieval-Augmented Generation (RAG) systems turn items into vectors and ask "which stored vectors are closest to this one?" Four ways to answer, from checking everything to a Hierarchical Navigable Small World (HNSW) graph — and the price each one pays.

Recall vs speed, over many queries

Recall@k = the fraction of the true k nearest neighbors a method returns (brute force is the answer key). Distances / query is the average number of distance computations — the expensive step when vectors have hundreds of dimensions. Uses the k, K, L, M, efConstruction and ef settings above, and 200 queries drawn near the data (seeded, so the numbers repeat).

Why vector databases use graphs and quantization. In 2 dimensions a k-d tree prunes almost everything. As the dimension grows, the query's ball crosses nearly every split line, so the tree ends up checking most points (switch the data to 64 dimensions and watch its column). Data-independent LSH needs many tables, and many candidates, to reach high recall. Graph indexes such as HNSW keep the number of distance computations small even in high dimensions, at the cost of a slower build, extra memory for links, and recall slightly below 100% (raise ef to buy it back). That is why libraries and databases such as Faiss, pgvector, and most dedicated vector databases offer HNSW. The other big family, used when vectors don't fit in memory, is quantization: an inverted file (IVF) groups vectors by their nearest of a few thousand centroids and searches only the closest groups, and product quantization (PQ) compresses each vector to a few bytes so distances can be approximated from lookup tables.

How to read this

  • The orange crosshair is the query q. Green points joined to q by lines are the current k best. Yellow points had their distance computed; every yellow point costs one unit in the "distances" counter. On the last frame, a red ring marks a true nearest neighbor the method missed.
  • k-d tree: each line splits a region in half at a median point (vertical lines split on x, horizontal on y). The dashed circle is the current k-th best distance. If the circle doesn't reach a split line, everything on the other side is skipped: those regions turn grey.
  • LSH: the lines of one table cut the plane into cells; a cell is a bucket. The tinted polygon is q's cell, purple points share it. Candidates (yellow) are the union over all L tables; only they get a distance computation.
  • HNSW: every point is on layer 0; a point reaches layer ℓ with probability (1/M)ℓ, so upper layers are sparse "highways". The search starts at the top, walks greedily to the closest node it can reach, drops a layer, and repeats. On layer 0 it keeps a list W of the best ef nodes (green) and a queue of candidates to expand (purple rings). Blue = the node being expanded.

Try this

  1. Brute force is the baseline. With n = 150, k = 3, brute force always computes exactly 150 distances. Every other method is trying to beat that number without losing recall.
  2. Watch pruning. In k-d tree mode, put the query inside a dense cluster. Most of the plane turns grey and the search computes only 10–25 distances. Then put the query in an empty corner: the circle is large, it crosses many lines, and the count goes up.
  3. Tune LSH. Set L = 1 and drag K from 1 to 12. Few lines means huge buckets (many candidates, high recall); many lines means tiny buckets that often miss the true neighbor. Then raise L: each extra table is another chance to catch it. Check the table: what K and L reach 100% recall, and how many candidates does it cost?
  4. Turn the ef dial. Choose the 64-dimension data and set ef = 1: with seed 3, HNSW finds about 79% of the true neighbors while computing distances to about 6% of the points. Set ef = 32: about 99% recall for about 15%. ef is picked at query time, with no rebuild. Now try M = 2: the graph is too sparse to navigate, and recall collapses whatever ef you choose.
  5. The curse of dimensionality. Run the benchmark on the 2-D points, then on 64 dimensions. The k-d tree goes from checking about an eighth of the points to checking almost all of them (still exact, but no faster than brute force). HNSW stays near 10%.
