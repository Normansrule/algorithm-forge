Counting in a stream

Billions of items fly past and you may keep only a few kilobytes. How many different items were there, and which ones were frequent? Watch an exact set, HyperLogLog (HLL), the 2022 Chakraborty–Vinodchandran–Meel (CVM) sampling algorithm, a Count–Min sketch and Misra–Gries counters read the same stream side by side, each trading a small, measured error for a tiny, fixed memory.

Error vs memory

Memory: 5 bits per HLL register; 32 bits per CVM buffer slot (an item stored as a 32-bit identifier).

How to read this

The stream
The strip at the top shows the newest items (blue = just processed). On a 🤔 frame the next item is shown in yellow before it is processed. Every summary sees each item exactly once, in order, and may never look back.
Exact set
Remembers every distinct item: green = new, yellow = seen before. It is always right, and its memory grows with the answer (here counted as 32 bits per distinct item; real words need more).
HyperLogLog
The 32 boxes are the item's hash. The purple low bits choose a register j; in the other 32 − b bits, the yellow leading zeros and the first 1-bit (green) give ρ = zeros + 1. Register M[j] keeps the largest ρ ever seen. A ρ of 10 happens about once per 210 hashes, so large registers mean many distinct items. Darker cells hold larger values; the cell just written is red. Duplicates hash identically, so they never change anything.
CVM
The grid is the buffer X (thresh slots). Each arriving item first forgets its old coin flip (it is removed if present), then is kept with probability p (green = kept now). When X fills up, a halving round flips a coin for every stored item: red cells are evicted and p halves. Every distinct item seen so far sits in X with probability p, so |X| / p estimates the count.
Count–Min
d rows of w counters, one hash function per row. An item adds 1 to one counter in each row (red). A point query reads those d counters (yellow outline) and answers the smallest (green): other items only ever add to a counter, so the answer is never too low, and it is at most εN too high with probability at least 1 − δ, where ε = e/w and δ = e−d.
Misra–Gries
k − 1 counters. A tracked item adds 1; a new item takes a free counter; with no free counter, every counter drops by 1 (red), which cancels k distinct items at once. The faint band after each bar is the guarantee: the true count lies between the counter c and c + N/k, and the tick marks the truth.

Try this

  1. Duplicates are free. Set items per step to 1 and step through the Zipf stream. Each time a common word such as “the” comes back, HyperLogLog, CVM's estimate and the exact set do not change, but Count–Min and Misra–Gries do. Answer the 🤔 question about the repeated word.
  2. Small counts. At the start almost every HLL register is 0, so the page switches to linear counting m · ln(m / V) (V = registers still 0) and is nearly exact. Watch the counter "mode" flip to the harmonic-mean estimate once the raw estimate passes 2.5 m.
  3. Halving rounds. Set thresh = 10 and watch CVM: every time the buffer fills, about half the cells turn red and p halves. Press 🎲 New seed a few times at the same N: the estimate moves around the truth. Raise thresh to 100 and the swings shrink.
  4. Space vs error. Run the error-vs-memory experiment. HLL's dots follow 1.04/√m, so 4 times the memory halves the error. CVM also improves as thresh grows, but at the same number of bits it is less accurate, because it stores whole items (32 bits) where HLL stores 5-bit registers.
  5. Heavy hitters. Choose the network-traffic stream and k = 6 (5 counters, N/k ≈ 16.7% of the stream). Only 10.0.0.7 (18% of the traffic) is guaranteed a counter; the 11% and 7% addresses keep being cancelled by the crowd of rare addresses. Switch to k = 16 (15 counters, N/k = 6.25%): now all three Internet Protocol (IP) addresses are above N/k, so all three hold counters at the end, each at most N/k below its true count. Count–Min overestimates rare items the most; try w = 4 and then w = 64 and query a rare address.
