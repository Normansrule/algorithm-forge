Cuckoo Hashing and Modern Filters

Give every key exactly two possible homes and let newcomers kick old keys out, like a cuckoo chick. That one idea gives hash tables with worst-case two-probe lookups, and filters that beat the Bloom filter on space and can delete. Finish with the xor filter, built by peeling a hypergraph.

Same memory for both: the Bloom filter gets m = 4·B·f bits, exactly the bits of the cuckoo filter's B buckets × 4 slots × f bits.

What's happening

Measured false-positive rate vs theory (at scale)

A cuckoo filter with 1,024 buckets × 4 slots is filled until an insertion fails (or 95% of slots are used). A Bloom filter gets the same number of bits and the best k = (m/n) ln 2. Then both are asked about 50,000 items that were never inserted, and the false-positive (FP) rate is the fraction that wrongly get "maybe".

How to read this

① Two tables, two hash functions
Key x may live only in T1[h1(x)] or T2[h2(x)]. A lookup checks those two cells and nothing else, so it costs at most 2 probes even in the worst case. Each cell shows its key and, in small print, the key's other home. Inserting always puts the new key in its T1 home; whoever was there is kicked out (the purple "in hand" box) and flies to its own other home, possibly kicking someone else. Orange arrows trace the kick-out chain.
When kicking never ends
If the chain returns to a configuration it has already been in, it is a cycle and would repeat forever. If it simply runs too long (MaxLoop rounds) we also give up. Either way: rehash, meaning pick new random hash functions (and grow the tables if the load factor α = n / 2m has reached 1/2), then re-insert everything.
② Fingerprints in buckets of 4
A cuckoo filter stores only a short f-bit fingerprint of each item, in B buckets of 4 slots. It never sees the item again after inserting, so it can't recompute h2 from the item. Partial-key cuckoo hashing solves that: i2 = i1 xor hash(fingerprint). Because xor undoes itself, any fingerprint's other bucket is "my bucket xor hash(me)", whichever bucket it is in now.
The Bloom filter beside it sets k bits per item. Probed bits are yellow, newly set bits red, a 0 bit that proves absence blue. Bits are shared, so a Bloom filter can't delete; the cuckoo filter just removes one copy of the fingerprint.
③ Xor filter
Each key touches 3 cells, one per segment. A key's fingerprint must equal the xor of its 3 cells. Building works backwards: repeatedly peel a cell that only one remaining key touches (push it on a stack), then pop the stack and set each key's private cell so its xor comes out right.

Try this

  1. A kick-out chain. In part ① press Classic example (7 keys, m = 11, h1(K) = K mod 11, h2(K) = ⌊K/11⌋ mod 11), then step through inserting 32. The tables are only 32% full, yet 32 kicks out 65, which kicks out 64, then 20, then 21, which kicks 32 itself back out; then 31 … After 12 kicks the tables are back in a state they have already been in: a cycle. The reason: 32 and six stored keys all have their T1 home in cells 9 or 10 and their T2 home in cells 1, 2, 4 or 5. That is 7 keys for 6 cells. No amount of kicking can fit them, so the sim rehashes with random functions.
  2. Worst-case lookup. After any build, look up a stored key and a missing key. Both take at most 2 probes, never a chain or a cluster. Compare with linear probing in the Hashing Lab.
  3. The 50% wall. Run the experiment with m = 2003. With two tables and one key per cell, the first failure comes at a load factor close to 0.5, and kicks per insert shoot up as α approaches it. That is why the bucketed version in part ② (4 slots per bucket) is used in practice: it reaches about 95%.
  4. Xor in action. In part ②, insert apple and answer the 🤔 question: i2 is i1 xor hash(f), bit by bit. Then insert 8 random items until a bucket overflows and watch fingerprints move to "my bucket xor hash(me)".
  5. Delete. Insert apple, then Delete it: the cuckoo filter answers "no" afterwards, while the Bloom filter still says "maybe" (it can't delete). Tick "let Delete clear Bloom bits", insert a few items, delete one, then look up the others: one may now be a false negative, which a filter must never produce.
  6. Space vs accuracy. Press Sweep f. With few bits per item the Bloom filter is more accurate; from about 11–12 bits per item (false-positive rates below roughly 0.5%) the cuckoo filter's dots drop below the Bloom filter's at the same space, and the gap widens as f grows. The reason: a Bloom filter needs 1.44 log₂(1/ε) bits per item for false-positive rate ε, the cuckoo filter (log₂(1/ε) + 3)/α. The 1.44 factor eventually beats the "+3". (The paper's semi-sorting trick saves about one more bit per item and moves the crossover to larger ε.)
  7. Peeling. In part ③ build the default keys and answer which key gets its value first. Then look up a non-member: it passes only if the xor of its 3 cells happens to equal its 8-bit fingerprint, about 1 in 256.
