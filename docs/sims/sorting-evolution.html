Sorting evolution: from insertion sort to Timsort, Powersort and pdqsort

The sorts inside Python, Java, Rust and C++ standard libraries are hybrids built from the classics you already know. They win because they notice structure: runs that are already sorted, lopsided splits, and repeated keys.

How to read this

  • Bars are the array. Red = just written or swapped, purple = pivot, green = known to be in its final place, grey = outside the range being worked on.
  • Timsort & Powersort mode: coloured bands under the bars are runs (already-sorted stretches). A dashed band is the run being found or extended right now. The run stack lists runs waiting to be merged; Z is the newest. Timsort keeps two rules true: |X| > |Y| + |Z| and |Y| > |Z|, so run lengths shrink fast going up the stack and every merge is between runs of similar size. During a merge, the small strip at the bottom is the temp buffer (a copy of the shorter run); faded cells are already used.
  • Powersort policy: same runs, same galloping merges, different decision about when to merge. Each boundary between two neighbouring runs gets a node power (the circled number): take the two runs' midpoints as fractions of n, write them in binary, and find the first digit where they differ. That is the boundary's depth in a perfectly balanced merge tree over the whole array. When a new run arrives, runs on the stack are merged while the boundary under the top run has a greater power than the new boundary, so deeper (more local) boundaries are always merged first. Computing a power needs only integer arithmetic on positions, never a key comparison, so the comparison counter is unchanged by the policy itself.
  • Introsort / pdqsort mode: the bracket shows the range being partitioned. Introsort spends one unit of its depth budget per level; at 0 it switches to heapsort. pdqsort instead counts bad partitions (one side smaller than one eighth), tries a capped insertion sort when a partition needed no swaps, and skips runs of keys equal to the previous pivot.
  • Counters count every key comparison (a < b) exactly. Writes count stores into the array (temp-buffer copies are not counted). Merge cost adds up the lengths of the two runs in every merge: the number of elements that pass through merges, the quantity Powersort keeps close to optimal.

Try this

  1. Demo, Timsort. Play the demo array (n = 36). The descending runs are reversed, short runs are extended to minrun = 5 by binary insertion, and the last merge enters galloping mode. Total: 102 comparisons. Top-down mergesort needs 122 on the same array, insertion sort 375.
  2. Powersort versus Timsort. Pick the shape Uneven runs and n = 64 in mode 1. Play it once with Merge policy = Classic Timsort, then switch to Powersort. The runs have lengths 29, 24, 8 and 3. Classic Timsort's length rule breaks when the 8-run arrives, so it merges 24 + 8, then 29 + 32, and finally drags all 61 elements through one more merge just to add the last 3: merge cost 157. Powersort gives the boundary between the two big runs power 1 (it sits near the middle of the array), so that boundary waits while the small runs on the right merge first: merge cost 110, and fewer comparisons too.
  3. Sorted and reversed. Pick Sorted, then Reversed, in Timsort mode. Both take exactly n − 1 comparisons: the whole array is one run (a reversed array is one strictly descending run that gets flipped).
  4. Few unique, pdqsort. Switch to mode 2, pick pdqsort and Few unique. Watch for the "many equal keys" step: once a pivot equals the previous pivot, every copy of that key is finished in one pass.
  5. Force the fallback. In mode 2 (teaching constants), choose Introsort, Safety limit = Tiny and any shape. After two levels of partitioning the depth budget is gone, so heapsort finishes every piece still bigger than the cutoff. With the standard budget this only happens on adversarial inputs, and it is exactly what saves introsort from quicksort's O(n²) worst case. pdqsort with Tiny switches to heapsort at its first bad partition (try Organ pipe).
  6. The race. Before pressing the button, answer the two questions. Then compare quicksort (first pivot) on Sorted (about n²/2 comparisons) with Timsort (n − 1). Look at Uneven runs to see where Powersort's policy pays off, and notice how often it ties with Timsort elsewhere. On Random with n = 1,000, Timsort and mergesort are within 1% of each other: when there is no structure, looking for it costs almost nothing.
