Skip List

A sorted linked list with express lanes. Each new key flips coins to decide how tall its tower is, and searches ride the high lanes, dropping down when they would overshoot. You get O(log n) expected search, insert and delete with no rotations or rebalancing at all.

What's happening

Skip list vs balanced Binary Search Tree (BST)

Build each structure from the same random keys, then search for every key once and average the number of key comparisons. "Balanced BST" is the perfectly balanced tree (the best any BST can do); "random BST" is a plain BST with keys inserted in random order and no rebalancing.

Where skip lists run

  • Redis sorted sets (ZADD, ZRANGE): a skip list plus a hash table, with p = 1/4 and at most 32 levels (ZSKIPLIST_P, ZSKIPLIST_MAXLEVEL in the source). Each forward pointer also stores a span, so rank queries are O(log n) too.
  • LevelDB: the in-memory write buffer (memtable) is a skip list with maximum height 12 that grows a level with probability 1 in 4.
  • RocksDB: the default memtable implementation is a skip list. Both are the "C0" level of a Log-Structured Merge-tree (LSM-tree).
  • Java: java.util.concurrent.ConcurrentSkipListMap and ConcurrentSkipListSet, sorted maps that many threads can update at once.

How to read this

Towers and levels
Every key is a tower of boxes. Level 0 (bottom) links all keys in sorted order. A key reaches level i + 1 only if it won another coin flip (probability p), so each level holds about a fraction p of the keys below it: an express lane. head (left) and NIL (right, key +∞) are sentinels as tall as the list.
The search path
Start at the top of head. Look at the next key on this level: if it is smaller than the target, move right; otherwise drop down one level. At level 0 the next key is either the target or proof it is absent. The orange line is the path; counters show right and down moves next to log₂ n.
update[ ]
While descending, insert and delete remember the last box visited on each level (purple). Those are exactly the boxes whose forward pointers must change: splice the new tower in after them, or route around a deleted one.
Expected height and space
A tower has height ≥ k with probability pk−1, so the expected height is 1/(1 − p) and the tallest tower is about log1/p n. Pugh's analysis bounds the expected search path by log1/p(n)/p + 1/(1 − p): about 2 log₂ n + 2 for p = 1/2.

Try this

  1. Follow a search. Press Example, type 19 and press Search. On level 3 the next key is 21 > 19, so drop. On level 2, ride right to 6; 21 is too big again, drop. On level 1, ride to 9 and 17, drop. On level 0 the next key is 19: found. That is 3 right + 3 down moves for n = 10, where a plain sorted linked list walks 7 nodes. The "pointers / key" counter shows measured vs expected (≈ 2 for p = 1/2).
  2. Choose the coins. Leave the flips as HHT and insert 23: two heads and a tail give a tower of height 3. Watch the three purple update[ ] boxes, then the three pointers being rewired (red), bottom level first.
  3. Grow the list taller. Type flips HHHHHT and insert 1. The tower is taller than the list, so the head grows and the new levels' update[ ] entries are the head itself.
  4. Delete. Delete 21 (a tower of height 4). Its predecessor on every level (purple) is rerouted around it, bottom level first. Then delete 1 from step 3: it was the only tower on the top levels, so the list's level shrinks.
  5. p = 1/4. Switch p to 1/4, clear the flips box, and Build with 30+ keys. Towers are shorter (1.33 pointers per key instead of 2) and paths a bit longer per level, but about the same total: 4·log₄ n = 2 log₂ n.
  6. Measure. Press Measure below. The skip list needs roughly twice the comparisons of a perfectly balanced BST (each level costs about 1/p moves) and more than a random BST, and its path stays under Pugh's bound. What you buy: the O(log n) expectation holds for every insertion order (a plain BST fed sorted keys becomes a linked list), and nothing is ever rotated. Switch p to 1/4 and measure again: fewer pointers per key, similar comparisons.
